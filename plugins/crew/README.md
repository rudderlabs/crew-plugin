# crew: the RudderCrew plugin for Claude

One install connects Claude to a Crew workspace and adds the skills that set it up and author its Agents.

## Install

In Claude Code:

```
/plugin marketplace add rudderlabs/crew-plugin
/plugin install crew@rudder-crew
```

What you need first, the one-line setup, signing in, claude.ai and Cowork, updating and troubleshooting: [the install guide](https://github.com/rudderlabs/crew-plugin#install).

Inside the plugin each skill is named `crew:<skill>`, for example `/crew:workspace-setup`. Skills also fire on their own when a request matches their description.

## How the skills fit together

- **Foundation** answers "how do I author any Crew Agent?" Every other skill links into it rather than repeating it.
- **Plays** answer "which signals, options and success event fit this use case?"
- **Channels** answer "how do I set this channel up, what can a message carry, and what works on it?"
- **Lists** answer "which people should this Agent work on?" `send-list` hands people to any Agent, whatever its channel.

A play and a channel combine at use time: a play hands the people it picks to a channel skill. Neither copies the other. `expand-audience` sits between a list of accounts and a channel skill: it finds the person at each account and hands them over on the lead event the channel skill triggers on.

## Workspace features

Some of what the skills use is a feature switched per workspace. The RudderStack team changes them; no one in the workspace can, in the app or over MCP. None is needed for an Agent deciding in Shadow. When a skill needs one that is off, it names the feature, tells the user to ask their RudderStack contact, and carries on with what works. Never look for a way around one. A feature a skill cannot read over MCP is never reported as off on a guess, default or not: the skill tells the user how to check it, as the table's last column says, and asks for the feature only when that check shows it is missing.

## Adding a skill

One PR under `plugins/crew/skills/<name>/`. Before it merges:

1. **One job.** Name it for the play or channel (`churn-deflection`, `customerio`), without a `crew-` prefix.
2. **A description that triggers.** Use the words a user would say, including the customer-name-only ask ("make an agent for Acme"). Frontmatter uses only the Agent Skills keys (`name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`); claude.ai refuses any other.
3. **Link the foundation, never copy it.** Point at `workspace-setup` for the schema, message writing and `check_body.py`.
4. **State a product fact once, and prefer the live source.** Each fact has one home, and every other file links to it: tools in `workspace-setup/references/mcp-map.md` by full name, feature defaults and who changes them in [Workspace features](#workspace-features), body rules and an Agent's runtime state in `workspace-setup/references/agent-schema.md`, the event-name and ingest rules in `workspace-setup/references/events-catalog.md`. Where Claude can read a fact live (`agent_bodySchema`, its own tool list, a tool's description or refusal), say where to read it instead of copying it. A copied fact drifts the day the product changes.
5. **Any workspace, any machine.** No local paths, hosts or workspace ids; check the prerequisites (token scope, features, channels) first.
6. **Human-only steps stay human.** Credentials, workspace features and the Live switch go to a person.
7. **Scripts are Python 3 standard library**, run by absolute path, and exit non-zero on a problem. One script per job: a skill that needs another skill's script runs it from that skill's folder rather than keeping a copy.
8. **Every rule names its evidence**: the run that showed it, described generically ("in an onboarding-email Agent, the first dry run…"). Customers read every file here, so no customer or prospect names, workspace names, internal paths, PR numbers or dates. The repository is public, so the same holds for commit messages, pull-request titles and descriptions, and review replies, and none of them says where a change came from (a call, a demo, watching someone set up): the root `CLAUDE.md` → "Public text" has the whole rule.
9. **Evals** under `evals/` for new skills: `claude plugin eval plugins/crew` runs each case with and without the plugin.
10. **`claude plugin validate plugins/crew` passes**, and the PR bumps `version` in `.claude-plugin/plugin.json`. Validate fails on a broken `plugin.json` or `hooks.json` but only warns on an empty `SKILL.md` and doesn't check that a hook's script exists, so it does not stand in for items 1 to 9.

Internal tooling that customers should never see (demo prep, for example) stays a plain skill outside this plugin.
